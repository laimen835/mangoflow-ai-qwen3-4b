## Не нарушать принятые решения

1. Официальные факты об академии — только из допустимых источников. Прежние
   ответы модели, ссылка без прочитанного текста и общая страница не являются
   доказательством конкретного утверждения. Интернет-поиск на каждый вопрос
   и свободный ответ по памяти при отказе RAG не реализованы.
2. Не смешивайте колледж, институты, кафедры, СПО и высшее образование. Фильтр
   подразделения применяется до top-k. При неоднозначности нужен вопрос.
3. Основная модель остаётся `qwen3:4b-instruct`. Ни смена модели, ни дообучение,
   ни включение reranker не считаются автоматически разрешённым улучшением.
4. `legacy-v1` остаётся активным. mMARCO-кандидат и BGE не прошли приёмку.
   Не включайте их ради более красивой архитектуры. Не меняйте префиксы
   Nomic в активном индексе без совместимой переиндексации и проверки.
5. Сохраняйте `POST /api/v1/chat`, NDJSON `/api/v1/chat/stream`, структуру
   sources и обязательные поля ответа. Новые usage-поля допустимы.
6. Не восстанавливайте жёсткий отсев по `focus_terms` только ради старого
   падающего теста. Остаточный общий `word_gate` активного поиска — отдельная
   известная проблема; её изменение требует оценки качества.
7. Сохраняйте исходный пользовательский текст в Message.content. Внутреннее
   разрешение контекста живёт отдельно в usage. Нейтральные социальные реплики
   не должны вытеснять тему; состояние уточнения принадлежит беседе.
8. Непроверенные тестовые материалы и требующие проверки документы не должны
   попадать в обычные ответы. Допуск OCR/СПО должен быть явным и привязанным
   к проверенному тексту. Не расширяйте правило СПО механически на все институты.
9. Точные пары и числитель/знаменатель не угадывать: нужны проверенные таблицы
   и официальная календарная привязка. Дата загрузки не означает актуальность.
10. Черновики писем, перевод и планы подготовки — отдельные задачи, без
    выдуманных официальных источников. Письма не отправляются. Не добавляйте
    без отдельного решения полноценного универсального репетитора.

## Безопасность и данные

- Не включать в Git и отчёты `.env*` с реальными значениями, ключи, пароли,
  токены CloudPub/ngrok, закрытые SSH-ключи, дампы, модели, сырые диалоги,
  приватные журналы и архивы. Не выводить целиком Settings или окружение.
- Секреты хранить только в приватных конфигурациях. Для диагностики печатать
  только заранее выбранные несекретные поля. Не переносить реальные значения
  в `.env.example`. IP/адреса личной инфраструктуры без необходимости не копировать.
- Публичный туннель подключается к `src/core/share.py`, а не к полному API.
  Закрыты admin/docs, локальная история, произвольные upstream-пути. Проверяйте
  изоляцию двумя отдельными cookie-клиентами; чужая история возвращает пустые
  `items` с HTTP 200, это не само по себе утечка.
- Ответы модели рендерить безопасными DOM-элементами, разрешая HTTP/HTTPS;
  не исполнять HTML. Официальные ссылки и номера [n] должны совпадать с контекстом.
- Не отправлять сообщения другим людям, не покупать тарифы, не удалять

## Проверки и отчётность

Запуск и точные команды находятся в `PROJECT_CONTEXT.md`. Тесты могут зависеть
от живой локальной БД, моделей и существующих документов: проверьте цель БД
до запуска. Используйте уникальный `--basetemp` на D. Не считайте весь набор
unit-only; `test_hybrid_search` может оставить явно тестовый документ.

Сравнения проводить на одинаковом снимке данных и фиксированном коде. Разделять
разработку и контроль по фактам; просмотренный контроль становится регрессией.
Показывать фактическую точность с источниками, Recall@4, неподтверждённые ответы,
время поиска, первого текста и полного ответа отдельно. Балл поиска — не
процент уверенности. Не объявлять 90% качества по прохождению фразовых сценариев.

Для docs-only правок проверяйте ссылки, команды, отсутствие секретов и diff;
не запускайте дорогие LLM-прогоны и переиндексацию без необходимости. Для кода
запускайте относящиеся к изменению проверки, затем требуемые регрессии. В отчёте
отличайте новый прогон, целевой повтор и исторический результат. Не скрывайте
известный сбой pytest. После изменения обновляйте эти документы, если состояние
проекта изменилось; не превращайте план в запись о выполненной функции.
